WebSharper for C#

One language for the whole web app: C#

WebSharper compiles C# to modern JavaScript and writes the glue between the tiers for you: the endpoints, DTOs, fetch calls and serialization that a separate frontend needs. The server, the browser and the contract between them are written, typed and refactored in the same language, with async/await, LINQ and records on both sides.

Get started See the generated JavaScript ↓
$ dotnet new websharper-spa -lang C# -o MyApp
One C# project MyApp.csproj
Shared.cs Remoting.cs Client.cs Site.cs
dotnet build

An ASP.NET Core app: sitelets, typed routes, RPC endpoints, auth and DI.

Browser

Readable ES2022 modules with native async, generators and classes, bundled for production.

Generated: RPC endpoints, client proxies, JSON 83 typed JS bindings

Debugging

Breakpoints in C#, all the way into the browser

Turn on source maps and the browser's developer tools show your C# files, not just the generated JavaScript. Pause on a line of Client.cs, step through it and inspect its variables, then step on into WebSharper's own libraries.

  • Browser: your .cs files in Chrome, Edge or Firefox DevTools, next to the sources of the libraries you use.
  • Server: the [Remote] method the client awaits stops in Visual Studio, Rider or VS Code, like any ASP.NET Core code.
  • One language in both debuggers: the same names, types and lines on each side of the call.

Why full-stack C#

Six reasons to write the frontend in C# too

If your backend is already in .NET, a separate TypeScript frontend means a second language, a second toolchain and a contract that can silently drift. Here's what you gain by writing both tiers in C#.

Built for AI-assisted development

Coding agents work best with a fast, strict feedback loop, and the C# compiler is one. Hallucinated members, wrong argument types and a client that's out of step with the server all fail dotnet build, so they never reach a browser.

  • Models have seen a huge amount of C#, and the code they write is checked by a compiler they can run.
  • A full feature fits in one context: the record, the endpoint and the UI that uses it, all in one language.
  • Typed bindings mean an agent can only call JavaScript APIs that actually exist, and our binding skill lets it generate new ones.
  • Every dotnet new template ships an AGENTS.md and agent skills, so your agent knows the project's conventions from the first prompt.

// agent: "add paging to product search"

agent › edit Client.cs

await Remoting.Search(query, page)

$ dotnet build

'Search' takes 2 arguments

Your agent can ask the compiler

dotnet ws mcp connects coding agents to the WebSharper Booster over MCP. Instead of guessing, the agent can look up what your last build reported, how a member translates to JavaScript and which RPC methods the server exposes.

WebSharper diagnostics C# → JS translation symbol search RPC methods

Booster Pro adds get_signature: exact C# signatures from your project and its references, with a warning when a .NET API has no JavaScript translation, so the agent doesn't write client code that can't compile.

// .mcp.json

{

"mcpServers": {

"--lang", "csharp"]

Needs WebSharper 11 and the dotnet-ws tool. Build once to start the Booster and give it something to answer about.

Type safety from the database to the DOM

RPC calls, routes, HTML templates and JavaScript libraries are all typed. A misspelled template hole, a broken link or a renamed field is a compile error, not a support ticket. And Rename, Find All References and Go to Definition reach into the client code too, so long-lived apps stay easy to change.

One team, one skill set

Your .NET developers can ship whole features without handing off to a frontend team. Code review, hiring and onboarding all happen in one language, and there's no second package ecosystem to keep current.

What compiles behaves like .NET

Integer overflow wraps, exceptions keep their .NET types and decimal stays exact (through math.js). Where JavaScript can't follow .NET, such as reflection or culture-aware sorting, WebSharper leaves the API out instead of shipping a lookalike, and points you to the browser API to use.

The .NET platform you already run

It's plain ASP.NET Core underneath, so your authentication, DI, EF Core, logging, NuGet feeds, CI and hosting all keep working. WebSharper is just another package in the project.

JavaScript you can read

No WebAssembly runtime to download and no opaque blob. You get ES modules whose classes and methods follow your C# closely, so you can read and step through them in the browser's developer tools. They come with TypeScript declarations too.

No glue code

Call the server like a local method

Mark a server method [Remote] and await it from the client. WebSharper generates the endpoint, the client proxy and the JSON, so you don't write routes, DTOs or fetch code.

1
Remoting.cs: an async server method that returns it.
2
Client.cs: a search box that awaits the call and renders a reactive list.
3
Shared.cs: a [JavaScript] record, used on both tiers.
4
Site.cs: a sitelet that renders the page on the server and hands the widget to the browser.
using WebSharper;

namespace Shop;

public static class Remoting
{
    static readonly Product[] Catalog = {
        new("Keyboard", 49.0),
        new("Monitor", 189.0),
        new("Mouse", 19.0)
    };

    // A typed server function; the client calls it like a local method.
    [Remote]
    public static Task<Product[]> Search(string query) =>
        Task.FromResult(Catalog
            .Where(p => p.Name.Contains(query, StringComparison.OrdinalIgnoreCase))
            .ToArray());
}

using WebSharper;
using WebSharper.UI;
using WebSharper.UI.Client;
using static WebSharper.UI.Client.Html;

namespace Shop;

[JavaScript]
public static class Client
{
    public static IControlBody SearchBox()
    {
        var results = Var.Create(Enumerable.Empty<Product>());

        return new Template.Main.SearchForm()
            .OnSearch(async e =>
            {
                // A remote call: arguments and results cross the wire typed.
                results.Value = await Remoting.Search(e.Vars.Query.Value);
            })
            .Results(results.View.DocSeqCached(
                (Product p) => p.Name,
                (Product p) => li($"{p.Name}: ${p.Price}")
            ))
            .Doc();
    }
}

using WebSharper;

namespace Shop;

// One type, used by the server, the client and the wire format.
[JavaScript]
public record Product(string Name, double Price);

using WebSharper;
using WebSharper.Sitelets;
using WebSharper.UI;
using static WebSharper.UI.Html;

namespace Shop;

public class Site
{
    [EndPoint("/")]
    public record Home;

    // The server renders the page; client(...) marks where the browser takes over.
    [Website]
    public static Sitelet<object> Main =>
        new SiteletBuilder()
            .With<Home>((ctx, endpoint) =>
                Content.Page(
                    new Template.Main()
                        .Title("Shop")
                        .Body(doc(
                            h1("Find a product"),
                            div(client(() => Client.SearchBox()))
                        ))
                        .Doc()
                )
            )
            .Install();
}

The compiler

C# in, idiomatic JavaScript out

WebSharper reads your code through Roslyn and translates C#'s semantics, not just its syntax. Pick a feature to see what WebSharper 11 emits for it. The output below is real compiler output, reformatted only.

C# 
public async Task<int> CountDown()
{
    var i = 0;
    while (i < 10)
    {
        await Task.Delay(100);
        i++;
    }
    return i;
}
JavaScript (WebSharper 11) 
CountDown() {
  return Task.FromAsync(async () => {
    let i = 0;
    while (i < 10) {
      await Task.Delay_1(100);
      i++;
    }
    return i;
  });
}

WebSharper 10 compiled a method like this to a hand-written state machine of about 50 lines. WebSharper 11 keeps your loop and your awaits, and wraps the async function in a .NET-compatible Task, so exceptions and continuations behave as in .NET.

C# 
public IEnumerable<int> Ticks()
{
    try
    {
        while (true)
            yield return 1;
    }
    finally
    {
        Disposed = true;
    }
}
JavaScript (WebSharper 11) 
Ticks() {
  return Iterate(function* () {
    try {
      while (true)
        yield 1;
    } finally {
      this.Disposed = true;
    }
  }.bind(this));
}

Sequences are real JavaScript iterables, and disposing an enumerator early still runs your finally blocks, as in .NET.

C# 
public record Person(string Name, int Age, int Score);

public static string[] TopNames(Person[] people) =>
    people
        .Where(p => p.Age >= 18)
        .OrderByDescending(p => p.Score)
        .Take(3)
        .Select(p => p.Name.ToUpper())
        .ToArray();
JavaScript (WebSharper 11) 
static TopNames(people) {
  return ofSeq(
    map((a) => a.Name.toUpperCase(),
      Take(
        OrderByDescending(
          filter((p) => p.Age >= 18, people),
          (p) => p.Score, new BaseComparer()),
        3)));
}

Where, OrderByDescending, Take and Select map to WebSharper's lazy sequence functions, so the query is evaluated lazily, the way LINQ to Objects evaluates it.

C# 
public struct Point
{
    public int X;
    public int Y;
    public void Move(int dx) { X += dx; }
}

public object Structs(Point p1)
{
    var p2 = p1;
    p2.X = 10;        // p1.X is still unchanged
    Nudge(p1);        // passed by value
    object boxed = p1;
    return boxed;
}
JavaScript (WebSharper 11) 
Structs(p1) {
  const p2 = Clone(p1);
  p2.X = 10;
  Examples.Nudge(Clone(p1));
  const boxed = Clone(p1);
  return boxed;
}

Assigning, passing, returning and boxing a mutable struct makes a copy, so the method above cannot change the caller's p1. Record structs work too.

Omitted arguments use the declared defaults, including when the method is called through a delegate.

{

TypeScript interop

Typed for TypeScript, too

Next to every JavaScript module, WebSharper writes a .d.ts declaration file. It's on by default. Your C# types, default parameters and return types reach TypeScript intact, so a TypeScript codebase can call your C# with full type checking and editor completion.

  • 1 Adopt it one module at a time. You don't need to rewrite your React or Angular frontend. Compile a C# module and import it from the TypeScript you already have.
  • 2 Write the rules once. Pricing, validation and permission logic live in one C# source that runs on the server and ships, typed, to the browser. The two copies can't drift apart.
  • 3 Publish to npm. Set "javascriptExport": true in wsconfig.json and you get a dead-code-eliminated folder with an index.js and an index.d.ts, ready for npm pack.
  • 4 Keep the safety net. When the C# signature changes, tsc flags every TypeScript call site that no longer fits, and coding agents get the same errors on both sides of the boundary.

Reactive UI

HTML templates become typed C# classes

Designers keep plain HTML. At build time every ws-hole, ws-var and event in it becomes a C# member, and .Bind() wires it to reactive Vars. This is the real app; open the Preview tab. 


                                            

                                            

        
using WebSharper;
using WebSharper.UI;
using WebSharper.UI.Client;

namespace CSharpTasks;

[JavaScript]
public static class App
{
    [SPAEntryPoint]
    public static void ClientMain()
    {
        // Reactive state: the page updates itself when these change.
        var tasks = ListModel.FromSeq(new[] {
            "Write the UI in C#",
            "Let WebSharper compile it to JavaScript"
        });
        var newTask = Var.Create("");

        new Template.Index()
            .Tasks(tasks.View.DocSeqCached((string task) =>
                new Template.Index.TaskItem()
                    .Title(task)
                    .Done(() => tasks.Remove(task))
                    .Doc()
            ))
            .NewTask(newTask)
            .Add(() =>
            {
                var title = newTask.Value.Trim();
                if (title != "") tasks.Add(title);
                newTask.Value = "";
            })
            .Remaining(tasks.View.Map(ts => $"{ts.Count()} to go"))
            .Bind();
    }
}


    

        
<div class="app" id="main">
    <h1>Today</h1>
    <form onsubmit="return false">
        <input ws-var="NewTask" placeholder="What needs doing?" />
        <button class="add" ws-onclick="Add">Add</button>
    </form>
    <ul ws-hole="Tasks">
        <li ws-template="TaskItem">
            <span>${Title}</span>
            <button ws-onclick="Done" title="Done">&#10003;</button>
        </li>
    </ul>
    <div class="remaining">${Remaining}</div>
</div>
